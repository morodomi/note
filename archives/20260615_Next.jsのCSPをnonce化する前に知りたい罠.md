# Next.js 16でCSPをnonce化する前に知りたい、Tailwindとhydrationの罠

Next.js 16（App Router）+ Tailwind CSS 4 の構成で、Content-Security-Policy の「unsafe-inline」を nonce 方式に置き換えようとした。ローカルでは全テストが通った。緑だった。だが本番に出る前に、2回止められた。

1回目は、コードレビュー。このまま出していたら hydration が失敗して画面が真っ白になるところだった。
2回目は、staging での確認。Tailwind のスタイルが全部消えていた。

どちらも「自分のコードには inline script も inline style も無い」と確認したうえで起きている。原因は、自分が書いていない場所にあった。同じ構成で CSP を厳格化しようとしている人が、まず確実に踏む2つの地雷だと思う。幸い本番ユーザーに出る前に捕まえられたので、その回避ルートを先に書いておく。

## やりたかったこと

セキュリティスキャンで、CSP の「script-src」と「style-src」に「'unsafe-inline'」が入っているのが MEDIUM の指摘として上がっていた。

「'unsafe-inline'」があると、攻撃者が inline の script や style を注入できたとき、CSP がそれをブロックしない。XSS 防御として穴が空いている状態だ。これを塞ぎたい。

定石は nonce 方式だ。リクエストごとにランダムな文字列（nonce）を生成し、許可したい要素にだけその nonce を振る。CSP には「この nonce を持つ要素だけ許す」と書く。「'unsafe-inline'」を消して「'nonce-xxxx'」に置き換える。Next.js の公式ドキュメントにも middleware で nonce を生成するパターンが載っている。

middleware（うちでは proxy.ts という名前）で nonce を作り、レスポンスの CSP ヘッダーに埋める。素直に実装した。ローカルの dev server で開いて、Console に CSP violation が出ないことも確認した。テストも通った。

そのローカル緑のコードが、レビューと staging で2回ひっかかった。

## 地雷1: script-srcを厳格化すると、hydrationが失敗して白画面になる

最初に止めてくれたのは、コードレビューだった。「このCSPだと本番で画面が真っ白になる」と。

理屈はこうだ。CSP を厳格化すると「Refused to execute inline script」で inline script がブロックされる。だが自分は inline script なんて書いていない。root layout に「script」タグも無いし、「dangerouslySetInnerHTML」も使っていない。Stripe も決済はサーバー側で処理していて、自前の inline script は足していない（外部ドメインの js.stripe.com は別途 script-src で許可するが、これは inline ではない）。事前にそう確認していた。だから「inline script は無い、layout は触らなくていい」と判断していた。

見落としていたのは、Next.js の App Router が**自分で吐く inline script**だった。

App Router の RSC（React Server Components）は、ストリーミングのために inline script を自動で挿入する。形は「self.__next_f.push(...)」だ。これは自分が書いたコードには現れない。ビルド後の成果物に初めて現れる。CSP を厳格化すると、この framework 製の inline script が nonce を持っていない。だから全部ブロックされ、hydration が走らず白画面になる。

確認方法はシンプルで、ビルドした HTML を grep するだけだ。

```bash
npm run build
grep -E '<script>|self\.__next_f' .next/server/app/*.html
```

レビューはまさにこれを実行して、「ビルド済みの _global-error.html に self.__next_f.push(...) が複数あるのに、nonce= 属性はゼロ件」と実測で指摘してきた。「自分のコードを見て inline は無い」と言っていた自分は、ビルド成果物を見ていなかった。

### 直し方: nonceを「リクエストヘッダー」にも転送する

ここがこの記事で一番伝えたい点だ。

最初の実装は、nonce を**レスポンスヘッダー**にしか入れていなかった。CSP を出すのはレスポンスだから、それで十分だと思っていた。違った。

Next.js は、**リクエストヘッダー**の「x-nonce」を読んで、自分が auto-inject する inline script（__next_f など）に nonce 属性を自動で付けてくれる。だから middleware で nonce をレスポンスだけでなくリクエストにも転送しないといけない。なお「x-nonce」という名前は Next.js 公式ドキュメントの例に倣ったもので、フレームワーク固定の規約名ではない（自分で middleware が付けて、render 側に渡るのが本質）。

```typescript
function nextWithNonce(request: NextRequest, nonce: string) {
  const requestHeaders = new Headers(request.headers);
  requestHeaders.set('x-nonce', nonce);
  return NextResponse.next({ request: { headers: requestHeaders } });
}
```

middleware の中で「NextResponse.next()」を呼んでいる箇所を、全部この「nextWithNonce(request, nonce)」に差し替える。これでフレームワークが request の nonce を拾い、RSC の inline script に nonce を付け、白画面が直った。

リダイレクトを返す経路は新しいリクエストが発生するので対象外。それ以外の通常レスポンスの経路（うちでは3箇所）を全部置き換える。

白画面とは直接関係ないが、同じレビューでもう1点指摘されたので直した。nonce のエントロピーだ。最初は「Buffer.from(randomUUID()).toString('base64')」で作っていたが、UUID v4 のエントロピーは 122 bit で、CSP nonce の推奨値 128 bit に少し足りない。base64 化は文字種を整えるだけでエントロピーは増えない。「randomBytes(16)」(128 bit) に変えた。

```typescript
import { randomBytes } from 'node:crypto';

const nonce = randomBytes(16).toString('base64'); // 128 bit
```

## 地雷2: style-srcはnonce + unsafe-inlineの「併用」が成立しない

白画面の対処が済んで staging に出したら、今度は Tailwind が崩れていた。

style-src も script-src と同じ調子で nonce 化していた。だが、React の「style={{...}}」のような動的 inline style 属性には nonce を付けられない（React の仕様で attribute に nonce を振る口が無い）。そこで「nonce は付けつつ、inline style 属性のために 'unsafe-inline' も併記しておけば両方動くだろう」と考えた。

これが通らなかった。白画面は直したはずだった。なのに staging を開いたら、スタイルが丸ごと抜けた素のHTMLみたいな画面が出てきた。しばらく固まった。

原因は CSP の仕様そのものだった。CSP Level 2 以降では、**style-src に nonce か hash が1つでも存在すると、'unsafe-inline' は自動的に無視される**。「厳格な指定があるなら、ゆるい 'unsafe-inline' は信用しない」という設計だ。つまり「nonce + 'unsafe-inline'」の併用という妥協案そのものが、仕様上ありえない。

ここで CSP の2種類の inline style を区別しておく。ひとつは inline の「style」要素（「style」タグそのもの。CSP では style-src で制御）、もうひとつは要素に付く動的な style 属性（React の style={{...}}。CSP では style-src-attr で制御）だ。

やっかいなのは、Next.js 16 + Tailwind CSS 4 が production build で両方を吐くことだった。inline の「style」要素は手元で6〜7個あり、加えて React の動的 style 属性も出る。style-src に nonce を入れた瞬間、併記した 'unsafe-inline' が無効化され、これらの inline style が全部ブロックされ、画面のスタイルが崩れた。

### 直し方: style-srcは厳格化を諦める（今回は）

正直に書くと、style-src は**元に戻した**。

```
style-src 'self' 'unsafe-inline'
```

script-src の nonce 化は維持した。XSS の主要な攻撃ベクタは script の注入なので、そこを厳格化できていれば当初の目的（unsafe-inline による XSS リスクの低減）はほぼ達成している。style 由来の攻撃は影響が限定的だ。

style-src を本当に厳格化するには、その前に「Tailwind と Next.js が production で inline style を出さない状態」を作る必要がある。動的 style 属性を CSS カスタムプロパティ（CSS variables）に逃がすなど。そこまでやらないと、style-src の nonce 化は今の構成では技術的に不可能だ。これは別タスクに切り出した。

「全部きれいに nonce 化」を目指していたが、「script-src は厳格化、style-src は現実解」で手を打った。

## 最終的に動いたCSP

2回ひっかかって、落ち着いた CSP がこれだ。

```
default-src 'self'
script-src 'self' 'nonce-{リクエスト毎に変わる値}' https://js.stripe.com https://vercel.live
style-src 'self' 'unsafe-inline'
style-src-attr 'unsafe-inline'
img-src 'self' data: blob: https://*.s3.ap-northeast-1.amazonaws.com
font-src 'self'
frame-src https://js.stripe.com
connect-src 'self' https://api.stripe.com
object-src 'none'
base-uri 'self'
form-action 'self'
```

ポイントは2つ。

- script-src だけ「'nonce-...'」で厳格化し、「'unsafe-inline'」を消した。ここが XSS 防御の主目的
- style-src は「'self' 'unsafe-inline'」のまま。nonce を入れると Tailwind が崩れるので、あえて入れない
- style-src-attr も「'unsafe-inline'」を明示。これは前述の動的 style 属性（React の style={{...}}）用。style 要素と style 属性で別ディレクティブになるので、両方に 'unsafe-inline' を残している

「https://js.stripe.com」「https://api.stripe.com」は Stripe 用、「https://vercel.live」は Vercel のプレビュー（Live）機能用に許可している。使っていなければ要らない。

## 教訓

同じ構成で CSP を厳格化する人へ、踏んだ順に。

1. **「inline 無し」はフレームワーク層まで見ないと言えない。** 自分のコードを grep して「script タグ無し」で安心してはいけない。Next.js App Router は RSC streaming で自分で inline script を吐く。「npm run build」してから「.next/server/app」の HTML を grep するまでが調査だ。

2. **Next.js で nonce を使うなら、レスポンスだけでなくリクエストヘッダーにも転送する。** 「x-nonce」を request headers に入れると、フレームワークが auto-inject する inline script に nonce を自動付与してくれる。レスポンスヘッダーだけだと本番で白画面になる。

3. **style-src の「nonce + 'unsafe-inline'」併用は仕様上できない。** nonce か hash があると 'unsafe-inline' は無視される。Tailwind や Next.js が inline style を出す限り、style-src の nonce 化は inline style を消してからの話になる。

CSP は「ローカルで violation が出ない」では検証になっていなかった。ビルド成果物と、フレームワークが何を吐くかまで見て、はじめて成立する。ローカルで全部緑だったのに、レビューと staging で2回ひっかかったのは、そこを見ていなかったからだ。本番ユーザーに出る前に止められたのは、正直、運が良かった。
