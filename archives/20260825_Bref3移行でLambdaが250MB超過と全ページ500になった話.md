# Bref 3移行でLambdaが250MB超過と全ページ500。upgrade guideに無い2つの罠

AWS から「provided.al2 ランタイムを廃止する」という通知が来た。同じ通知、あなたのところにも届いていないだろうか。うちは Laravel on Lambda（Bref）の環境を、Bref 2 から 3 に上げた。変更は composer.json の 2 行と serverless.yml の 1 行。公式の [リリース記事](https://bref.sh/news/03-bref-3.0) には「the upgrade should be smooth」と書いてある。信じた。

結果、dev へのデプロイが Lambda のパッケージサイズ上限で落ちた。直して再デプロイしたら、全ページ 500。

同じ通知を受けて同じ移行をする人は、これから増えると思うので、upgrade guide に書いていない 2 つの地雷を書いておく。

## 環境・前提

- PHP 8.3 / Laravel 11
- bref/bref 2.3.11 → 3.0.7
- bref/laravel-bridge 2.4.4 → 3.0.8
- Serverless Framework v3 + serverless-lift、Zip デプロイ（コンテナイメージではない）
- CI は CodeBuild。buildspec で composer install → テスト → sls deploy

Lambda 関数は web（php-fpm）と SQS ワーカーの 2 種類。PHP のバージョンは今回触っていない（理由は末尾の反論欄に書いた）。

コンテナイメージでの運用、Symfony、PHP 8.2 未満の環境は試していない。この記事はあくまで上の構成での話だ。

## きっかけ: provided.al2 の廃止日程

AWS 公式の [Lambda runtimes](https://docs.aws.amazon.com/lambda/latest/dg/lambda-runtimes.html) にある日程はこうだ。執筆時点の表なので、実施直前に必ず見直してほしい。AWS は日程を変える。

- provided.al2 の deprecation: 2026 年 7 月 31 日
- 新規関数の作成ブロック: 2027 年 2 月 1 日
- 既存関数の更新ブロック: 2027 年 3 月 3 日

怖いのは 3 つ目だ。更新ブロック日を過ぎると、provided.al2 の関数はコードも設定も更新できなくなる。つまり「Bref 3 に上げてみて、ダメだったら戻す」というロールバックの選択肢が消える。戻す先が更新不可なのだから。

Bref 3.0 は Amazon Linux 2023 ベースで、ランタイム指定は「provided.al2023」になる。上げること自体に迷いはなかった。

## やったこと（ここまでは smooth だった）

Bref をバージョンアップするため、composer.json の bref/bref と bref/laravel-bridge の 2 行を「^3.0」にして、依存ごと更新。

```bash
composer update bref/bref bref/laravel-bridge --with-all-dependencies
```

serverless.yml は「provider.runtime」を「provided.al2」から「provided.al2023」に変えるだけ。関数側の「runtime: php-83-fpm」「php-83」はそのままで通る。なお、うちの serverless.yml は provider.runtime を古くから明示していたので変えたが、関数側の runtime だけ指定している構成なら upgrade guide 上この変更は要らない。

ローカルでテストは全部通った。composer audit の勧告は移行前より減った。ここまで 1 時間かかっていない。

## 地雷1: デプロイパッケージが 250MB 上限を超える

dev にデプロイしたら、CloudFormation がロールバックした。Lambda の「関数コード + レイヤー」を合わせた展開後のサイズが 250MB（262,144,000 バイト）を超えていた。Zip そのものの大きさではなく、解凍した後の合計だ。この上限を踏むと Lambda 側は次の定型エラーを返す（続けて実サイズが表示される）。

> Function code combined with layers exceeds the maximum allowed size of 262144000 bytes

Bref 2 のときは収まっていた。何が増えたのか。

「--with-all-dependencies」を付けたので、composer update で 70 パッケージが一緒に上がっていた。laravel/framework も aws/aws-sdk-php も入っている。vendor が太った。それだけなら、まだ収まったかもしれない。

本当の原因は、太る前から抱えていた無駄だった。

- buildspec が composer install を「--no-dev」なしで回し、その vendor をそのままパッケージングしていた
- serverless.yml の「package.patterns」が、docs や DB のダンプ置き場、CI のレポート成果物を除外していなかった

同梱されていた dev 依存は、phpstan、pint、faker、phpunit、psysh。テストと静的解析は pre_build で終わっているのに、本番の Zip に入っていた。dev 依存だけで数十 MB。

Bref 2 の頃は、この無駄を抱えたままでも 250MB の下にいた。だから気が付かなかった。

### 直し方

buildspec の「sls deploy」の直前に、dev 依存を落とす 1 行を入れる。

```bash
composer install --no-dev --optimize-autoloader
```

テストは pre_build で dev 依存込みで走らせ、パッケージングの直前に落とす。順番が大事で、先に落とすとテストが動かない。

serverless.yml の除外パターンも足す。案件固有のディレクトリ名は、一般的なものに置き換えてある。

```yaml
package:
  patterns:
    - '!node_modules/**'
    - '!storage/**'
    - '!tests/**'
    - '!docs/**'
    - '!.github/**'
    - '!reports/**'
    - '!coverage-report.xml'
    - '!unittest-report.xml'
```

これで数十 MB の余裕ができた。コンテナイメージへの移行は検討していない。必要なかった。Zip のまま無駄を削ったら収まった。

## 地雷2: 全ページ 500。新しい laravel-bridge は「既存の compiled view」を尊重する

サイズを直して再デプロイ。今度はデプロイが通った。/login は 302 で Cognito に飛ぶ。Laravel は起動している。ミドルウェアも動いている。

トップページを叩いたら 500。管理画面も 500。Blade を描画するページが全滅していた。

原因は、laravel-bridge の 2.4.4 と 3.0.8 の間で「view.compiled」の扱いが変わっていたことだ。

2.4.4 の BrefServiceProvider は、Laravel の「view.compiled」を無条件で /tmp 配下に上書きしていた。Lambda で書き込めるのは /tmp だけなので、Blade のコンパイル先を強制的にそこへ向ける。何が設定されていようが関係ない。

3.0.8 は条件付きになっている。[3.0.8 の BrefServiceProvider](https://github.com/brefphp/laravel-bridge/blob/3.0.8/src/BrefServiceProvider.php) を読むと、こう書いてある。

```php
$currentCompiledPath = Config::get('view.compiled');
if (! is_string($currentCompiledPath) || ! is_dir($currentCompiledPath)) {
    Config::set('view.compiled', StorageDirectories::Path . '/framework/views');
}
```

設定済みのディレクトリが実在するなら、そのまま使う。実在しないときだけ /tmp に向ける。

この 500 の再現条件は、compiled view の出力先を Zip の中に向けていること。Laravel 標準の「view.compiled」は storage/framework/views で、storage/ はパッケージから除外するのが普通だから、標準構成ならディレクトリが実在せず /tmp に向く。500 にはならない。うちは config/view.php で compiled 先を resource_path('cache') に変えていた。ビルド時に作ったキャッシュを Zip に同梱したかったからだ。

うちの buildspec は「php artisan view:cache」を回していた。resources/cache 配下にできた compiled view を、そのまま Zip に同梱していた。新しい bridge はそのディレクトリが「実在する」と判定し、そのまま使った。使った先は /var/task の下、Lambda では read-only だ。Blade がコンパイル結果を書き込もうとして落ちる。全ページ 500。

### v3 が変えたのではなかった

最初は「v3 が挙動を変えた」と思っていた。この記事の初稿もそう書いていた。

調べ直すと、この is_dir 条件は v3 ではなく、v2 系のマイナー **2.7.0**（2025 年 9 月）で入っていた。[PR #188「Allow pre-compiling views before deployment」](https://github.com/brefphp/laravel-bridge/pull/188) だ。デプロイ前にプリコンパイルしてコールドスタートを速くする、という前向きな変更で、2.7.0 の release notes に 1 行だけ載っている。

うちは 2.4.4 から 3.0.8 に一気に飛んだ。だから v2/v3 の差に見えた。2.7.x をすでに使っている人は、この地雷を踏まない。

Bref 3 の upgrade guide にも、laravel-bridge 3.0.0 の release notes にも、この件は書かれていない。書かれているのは 2.7.0 の notes の 1 行だけで、読んでも「同梱済みのキャッシュがあると 500 になる」とは分からない。3.0.0 の notes と upgrade guide は読んでから移行した。飛ばした 2.5 から 2.7 の notes は読んでいなかった。

### さらに嫌な事実

同梱していた compiled view は、Bref 2 の時代から一度も使われていなかったはずだ。

Blade のコンパイル済みファイル名は、テンプレートの絶対パスのハッシュで決まる。CodeBuild 上で作ったキャッシュのハッシュと、Lambda 上の /var/task から解決されるパスのハッシュは一致しない。2.4.4 が /tmp に上書きしていたので、Lambda はいつもランタイムでコンパイルし直していた。view:cache は、ビルド時間を食うだけの儀式だった。

git log を見たら、view:cache を buildspec に入れたのは 1 年半前だった。1 年半、意味のないコマンドを毎回のビルドで回していた。古い bridge の寛容さがそれを隠していた。

### 直し方

view:cache を buildspec から消す。resources/cache をパッケージから除外する。

```yaml
package:
  patterns:
    - '!resources/cache/**'
```

これで is_dir 判定が偽になり、/tmp へのフォールバックが効く。挙動は 2.4.4 のときと同じ「ランタイムコンパイル」に戻る。

プリコンパイルの恩恵を捨てたくない人は、別の道もある。Laravel には「view.relative_hash」という設定があり、true にするとコンパイル済みファイル名が相対パスのハッシュになる。ビルド環境と Lambda でパスが違っても一致するので、PR #188 の意図どおりデプロイ前の view:cache が効く。うちは試していない。まずランタイムコンパイルで元の挙動に戻すことを優先した。

## 前バージョンの寛容さが、設定の腐敗を隠す

2 つの地雷に共通することがある。どちらも Bref 3 が壊したのではない。Bref 3 のレイヤー自体はむしろ小さくなっている（[公式リリース記事](https://bref.sh/news/03-bref-3.0)）。古い構成は、容量の余裕と無条件の /tmp 上書きという別々の形で、設定の無駄を吸収していた。新しい構成では、その吸収がなくなっただけだ。

- dev 依存を本番 Zip に同梱していた。容量に余裕があったから気付かなかった
- 使われない compiled view を同梱していた。2.4.4 が無条件に /tmp へ上書きしていたから気付かなかった

「動いている設定」と「正しい設定」は別物で、その差は前の構成の寛容さが吸収している。major アップは、その吸収がなくなる瞬間だ。移行作業というより、設定の棚卸しだった。

もう一つ。マイナーを 3 つ飛ばしたら、その間の 1 行の release note を読み飛ばしていた。棚卸しの対象は、自分の設定ファイルだけじゃない。飛ばしたバージョンの notes も含む。

公式の smooth を信じた自分に呆れた、というのが正直なところだ。composer 2 行と yml 1 行で終わると思っていた。実際、その 3 行は smooth だった。smooth じゃなかったのは、自分が 1 年半放置していた buildspec のほうだ。

## 先回りしておく反論

「--no-dev してないのが悪い」。その通りだ。ただ、2.4.4 では収まっていたので気付く契機がなかった。この記事は「気付く契機は major アップで来る」という話だと思ってほしい。

「Lambda で view:cache するのが間違い」。半分正しい。ただ、無意味だと気付けなかったのは古い bridge が黙って上書きしていたからで、新しい bridge になって初めて表面化した。

「コンテナイメージにすれば全部解決」。250MB の壁は消える。ただし Lambda の package type は Zip から Image に変更できず、スタックを作り直す並行運用が要る。小規模な環境にはコストが見合わない。Zip で収まるなら Zip でいい。

「PHP も一緒に上げればよかった」。上げなかった。変更変数を増やすと、壊れたときにどれが原因か分からなくなる。今回は Bref と OS だけを変えたから、2 つの地雷を素直に切り分けられた。

## 原因特定は Claude Code がやった

この記事の内容は、自分が vendor を読んで見つけたものではない。

dev の 500 を伝えた。渡したのは CloudWatch のスタックトレースと、「2.4.4 では動いていた。変更は composer 2 行と yml 1 行だけ」という差分情報。Claude Code は vendor の中の laravel-bridge 3.0.8 の BrefServiceProvider を読み、2.4.4 と比較した。is_dir の条件が増えている、と一発で当てた。権限や /tmp を疑って迷走することもなかった。

もう一つ助かった場面がある。移行計画の段階で、Web 検索のまとめ記事を根拠に日付を書いていた。「provided.al2 の更新ブロックは 2026 年 9 月 30 日」と。計画のレビューを Codex にかけたら、AWS の公式表では 2027 年 3 月 3 日だと BLOCK が付いた。ロールバック期限を 5 か月も短く見積もっていた。一次ソースを見ろ、と AI に言われた。

AI に計画を書かせて、別の AI にレビューさせる。この構成のありがたみは、こういう地味な日付の誤りで実感する。

ただし、AI が「v3 が変えた」と言ったのをそのまま信じて初稿を書いたのも自分だ。2.7.0 起源だと分かったのは、記事を出す前にもう一度ソースを当たったからで、AI の一発回答にも一次ソースの確認は要る。

## まとめ

- provided.al2 は更新ブロック日（公式表で確認）を過ぎるとロールバック不能。それより前に上げる
- Bref 3 移行の 3 行の変更自体は smooth
- 地雷1: vendor 肥大で 250MB 超過。sls deploy 直前に composer install --no-dev、package.patterns で不要ディレクトリを除外
- 地雷2: laravel-bridge 2.7.0 以降（3.x 含む）は view.compiled のディレクトリが実在すれば尊重する。compiled 先を Zip 内に向けて同梱していると、絶対パスの違いでキャッシュが一致せず、read-only なディレクトリへ再コンパイルしようとして 500。同梱をやめて /tmp に戻すか、view.relative_hash で一致させる
- 上げる前に、buildspec と serverless.yml を「今の Bref が黙認している無駄はないか」という目で読み直す。飛ばしたバージョンの release notes も読む
