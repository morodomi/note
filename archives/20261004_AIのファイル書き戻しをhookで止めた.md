# Claude Codeのpython書き戻しをhookで止めた。3万件のログで範囲を決めた

最近、Claude Codeの画面にpythonが流れてくることが増えた。ファイルを1行直すだけでも、Editツールを使わずにpythonを書く。Opus 5.5あたりから増えた気がしている。数えてはいない。

```python
python3 - <<'EOF'
from pathlib import Path
p = Path("notes.md")
s = p.read_text(encoding="utf-8")
s = s.replace("古い文", "新しい文")
p.write_text(s, encoding="utf-8")
EOF
```

ファイルを読んで、置き換えて、丸ごと書き戻す。動くし、結果も正しい。

しばらく眺めていて、心配になった。私は同じフォルダで、Claude Codeのセッションを2つ以上動かすことがある。片方がこうやって丸ごと書き戻したら、もう片方が入れた変更は黙って消えるのではないか。同じ使い方をしているなら、他人事ではないと思う。

ルールの置き場所は、memory、CLAUDE.md、PreToolUseのhook、Claude Codeのmodと4つ考えた。Claudeと相談しながら進めて、最後はhookに落ち着いた。止める範囲は、過去のセッションで実際に打たれたBashコマンド3万件あまりを見て決めた。その過程で罠を3つ踏んだ。最後の1つは、止めるための文面が抜け道を案内していた、というものだった。

---

## 丸ごと書き戻しの何が怖いのか

セッションを並べて動かすのは、とくにObsidianのvaultだ。メモの整理と調べものを並行させている。

ここで丸ごと書き戻しが起きると、こうなる。

1. セッションAがファイルを読む
2. セッションBが同じファイルの別の箇所を直す
3. セッションAが、1で読んだ内容に自分の修正を足して、ファイル全体を書き戻す

Bの修正は消える。エラーも警告も出ない。

Editツールなら、指定した文字列を置き換えるだけだ。Bが別の箇所を直していても、そこには触らない。差分だけが当たる。

正直に書いておくと、この事故はまだ起きていない。起きる前に塞いだ話だ。「git worktreeで分ければいい」という意見もあると思う。ただvaultは、同じ作業場を複数のセッションで触る前提の場所なので、分ける対象にならない。

## 原因の見立ては、system prompt

なぜEditではなくpythonなのか。見立てはある。今のauto modeのsystem promptには、こういう一文が入っている。

> make small, mechanical file changes with sed, heredocs, or short scripts instead of the dedicated Read, Edit, or Write tools

小さな機械的な変更は、sedやheredocや短いスクリプトでやっていい、という意味だ。ただ、この文には続きがある。

> prefer Edit or Write when a shell edit would be fragile, such as exact or multi-line replacements

壊れやすい置き換えならEditを使え、とも書いてある。冒頭の1行置換は、むしろこっちに当たる。だから「system promptのせい」とは言い切れない。シェルでの書き換えを勧める文言が入っていて、モデルがそれを広めに読んでいるように見える。言えるのはそこまでだ。悪気がないのは確かだと思う。

## memory、CLAUDE.md、hook、mod

ルールをどこに置くか。実際にたどった順に書く。

最初はmemoryだった。Editを使ってほしいと伝えたら、Claudeがその場でmemoryに「pythonで丸ごと書き戻さない」と残した。ただ、memoryはそのプロジェクト（このときはvault）のものだ。ほかのフォルダで開いたセッションには効かない。

次にグローバルのCLAUDE.mdに移した。「既存ファイルの変更はEditで行う。system promptがシェルでの書き換えを勧めていても、こちらを優先する」。memoryのほうは重複になるので消した。

ここでClaudeに釘を刺された。CLAUDE.mdは強制ではない。公式ドキュメントにも書いてある。CLAUDE.mdは「強制される設定ではなく文脈」。必ず止めたいならPreToolUseのhookを使え、と（[Claude Code公式: memory](https://code.claude.com/docs/en/memory)）。

8月に書いた記事の結論もまさにそれだった。CLAUDE.mdに書いたルールは、AIが忘れれば終わりだ。

[CLAUDE.mdに思想を書いてもAIは守らない。開発哲学は仕組みに埋める](https://note.com/morodomi/n/nc30de34d8222)

Claudeの提案は「まずCLAUDE.mdで様子を見て、それでも続くならhookを足す」だった。誤検知が出やすいから、という理由だ。私は様子を見なかった。2分後には、hookで止める案を出していた。

modを考えたのは、hookを作り終えた後だ。Claude Codeのmodは、画面にペインを出したり、イベントを書き換えたりできる。止める役もmodに移したほうがいいのか。「確率論的な感じ？」とも聞いた。

答えは、modもhookと同じで、決まったイベントで必ず動く。機械的だ。確率的なのは、モデルが読んで守るかどうかを決めるCLAUDE.mdやmemoryのほうになる。止めるだけならhookで足りていて、modの強みは画面のほうにある。なので止める役はhookに残した。

## 止める範囲は、実際のログで決めた

Claude Codeにはこう頼んだ。今までのセッションで自分が使ったpythonでの書き換えコマンドを、PreToolUseで禁止する。止めたら「Edit/Writeを使え」と出す。良い提案内容？可能？

可能だった。で、まず「何を止めるか」を決めるために、過去のセッションのログに残っているBashコマンドを全部抜き出して、どんな形でファイルに書いているかを分類した。作業当日で35,300件。範囲は、この分類で見えた実例から決めた。

数字は後日、完成したhookの判定をそのまま過去ログに当てて数え直した。古いログが一部消えていて、総数は33,590件。このうちhookが止める形に一致したのは4,474件、13.3%だった。新しく作るファイルへの書き込みも混ざっているので、全部が既存ファイルの書き換えではない。

- インラインのpythonで書き込み: 3,217件
- heredoc・echo・printfでの追記や上書き: 777件
- sed -i: 411件
- perl -pi: 49件
- node -eで書き込み: 20件

heredocの中身で多かったのは、開発サイクルの進捗メモへの追記と、メモリファイルへの追記だった。perl -piは、ほぼバージョン番号の書き換え。

逆に、止めなかったものもある。tee、cp、mvだ。「多分使っていないと思うけど」と思いながら確かめたら、書き換えには本当に使っていなかった。teeは一時ファイルへの出力、cpはバックアップ、mvは名前の変更だけ。だから対象から外した。ただ、インラインのpythonの中でshutil.copyやos.renameを呼ぶ形は、pythonの書き込みとして止めている。

ここは割り切りだ。抜け道を全部ふさぐのは目的ではない。モデルは迂回しようとしているわけではなく、シェルで書くのが手近だから使っているだけだ。実際に使われている形を止めて、Editに誘導できれば十分だと考えた。

例外の置き方も決めた。

- インラインのpythonは、書き込み先が/tmpでも止める。書き込み先で例外を作ると判定が複雑になり、そこが抜け道になる
- heredocやリダイレクトは、/tmp・スクラッチパッド・/dev/null宛てなら通す。一時ファイルを書くのは正しい使い方なので
- スクリプトファイルの実行（python3 gen.py など）と、読むだけのインラインは通す
- sed -iとperl -iは、書き込み先を見ずに止める

## hookの形

もともとBash用のhookがあった。rm -rfや--no-verifyを止めるシェルスクリプトだ。そこに3つ目のチェックを足した。

```sh
# 3) 既存ファイルを Bash で書き換えるコマンド（python・sed -i・perl -i・heredoc など）は Edit / Write へ誘導する
#    複数セッションが同じファイルを触るとき、丸ごと書き戻しが他のセッションの変更を消すため。判定は rewrite_guard.py
REASON=$(printf '%s' "$CMD" | python3 "$(dirname "$0")/rewrite_guard.py")
if [ $? -eq 3 ]; then
  echo "$REASON" >&2
  exit 2
fi
```

PreToolUseのhookがexit 2で終わると、ツールの呼び出しは止まる。そして標準エラーの内容がClaudeに返る（[公式: hooks guide](https://code.claude.com/docs/en/hooks-guide)）。止めるだけでなく、次にどうするかを伝えられる。

判定はPythonのスクリプトに切り出した。理由は次の罠の1つ目だ。

## 罠1: 1行ずつのgrepでは判定できない

最初はシェルのgrepで済ませるつもりだった。別のモデルにレビューさせたら、2つ指摘された。

1つ目。冒頭のpythonの例を見てほしい。「python3 -」は1行目にあり、「write_text(」は6行目にある。1行ずつ見るgrepでは、この2つの組み合わせを判定できない。

2つ目。perlには-MTime::HiResのようなオプションがある。この中の「i」を、その場で書き換える-iと取り違える。

どちらも、言われればそうだとしか言えない。判定をPythonに移して、2段階にした。まずheredocの本文を除いた部分で、「python3 -」がコマンドとして呼ばれているかを見る。そのうえで、write_textのような書き込みの語は、本文も含めた全体から探す。

## 罠2: 引用符の中の > をリダイレクトと間違える

テストを先に書いた。止める例19件、通す例25件、hook経由の確認2件で、計46件。例は過去のログで実際に使われたコマンドから、思いつく形を拾った。

テストが通ったので、次に過去のコマンド全件に当ててみた。すると、止めなくていいものを止めていた。

```sh
printf "  %-30s -> " "$u"
```

URLを並べて表示するための書式だ。引用符の中の「>」を、ファイルへのリダイレクトと読んでいた。echoで「=== a > b ===」と区切り線を出すコマンドも、同じ理由で止めていた。

テストの例を自分で選んでいる限り、この形は拾えなかったと思う。全件に当てて初めて出てきた。引用符の中を無視して区切りとリダイレクトを読む、小さな字句解析に置き換えた。実ログに当てる工程がなければ、誤検知を抱えたまま入れていた。

## 罠3: 止める文面が、抜け道を案内していた

一番ひやっとしたのはこれだ。

最初の文面は、インラインのpythonを止めたとき「スクリプトファイルにして実行して」と案内していた。スクラッチパッドに書くような正しい用途もあるので、親切のつもりだった。

でも、モデルの側から読むとこうなる。「同じ書き戻しを、スクリプトファイルに移せば通る」。抜け道の案内そのものだ。仕上げ前の見直しで気づいたので、普段の作業でこの迂回が起きたわけではない。

hookの標準エラーは、Claudeへのフィードバックとして読まれる。つまり止める文面は、ただのエラーメッセージではなくプロンプトだ。今はこう返している。

```text
BLOCKED: インラインの python でファイルに書き込んでいる。既存ファイルの変更は Edit ツール、新規作成は Write ツールを使う。計算や変換が必要なら、結果を標準出力に出してから Edit で当てる。スクリプトから書き込んでよいのは、新しく作る出力ファイルだけ。
```

最後の一文で新規ファイルだけ許しているのは、新しく作るファイルなら、他のセッションの変更を消しようがないからだ。「スクリプトにすれば通る」と読める書き方になっていないことも、テストで確かめている。文面のテストを書くとは思っていなかった。

## 入れた後、実際どうなったか

判定にかかる時間は1回あたり約31msで、遅さは感じない。

導入から1日たったところで、ログを見てみた。その間に打たれたBashは約2,300件。実際に止まったのは10件ほどで、全部が最後の1時間あまりに固まっていた。

最初の23時間は、hookの出番がなかった。書き換えの形のコマンドが、ほぼ打たれていない。導入前の1週間は、Bashの23.8%がこの形だった。CLAUDE.mdが効いたと言いたいところだが、Editの回数も増えていないので、単にファイルを直す作業が少なかったのかもしれない。

最後の1時間は、Editを100回以上使う、ファイルを直す作業が続いた時間だった。CLAUDE.mdに書いてあっても、そこで書き換えが10件ほど出てきて、hookが止めていた。

止まったもので多かったのは次の2つ。

- 開発サイクルの進捗メモに「cat >>」で追記しようとしたもの
- 「sed -i」でフェーズ名を書き換えようとしたもの

止められた後は、Editで同じ変更を当て直していた。スクラッチパッド内のファイルを止められたケースでは、許可されている一時領域への書き直しに切り替えていた。

見た範囲では、teeなどで迂回しようとした例はなかった。実質1時間あまり・10件ほどなので、まだ何とも言えない数ではある。

一方で、誤検知も2つ見つかった。

- スクラッチパッドに cd してから、相対パスで「cat > review_prompt.txt」と書いたものが止まった。一時領域かどうかをパスの文字列だけで判定していて、cdを追っていないからだ
- スクラッチパッド内のファイルへの「sed -i」も止まった。sed -iは書き込み先を見ずに止めている

どちらも実害は小さく、モデルは別のやり方ですぐ進んだ。ただ、3万件のログで潰したつもりでも、本番に出せばまだ出てくる。

## 正直な留保

- Codexには効かない。hookはClaude Codeの中のBashにしか掛からない。Codexに任せた作業の中でのcat >>は素通りする
- Editが「読んだ後に別のセッションがファイルを変えていたら止まる」かどうかは確かめていない。言えるのは、差分だけを当てるので、他の箇所を消さないところまで
- 個人の開発環境の話だ。チームで同じ強度で効くかは分からない

8月の「開発哲学は仕組みに埋める」では、思想は語るものではなく仕組みに埋めるものだ、と書いた。今回やってみて付け足したいのは、埋めた仕組みの文面もまたAIに読まれる、ということだ。止めるつもりで書いた1行が、迂回のやり方を教える1行になっていた。結局、止める文面もちゃんと書かなきゃいけなかった。
