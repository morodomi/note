## 候補 #1: 開発手法60年史を並べたら、AI時代の組織開発の答えが見えた（仮）

- **ステータス: ネタ登録（2026-08-04 筆者持ち込み。執筆時期未定）**
- ソース: 筆者持ち込み + クライアントCTOとの議論 + 技術講義・dev-crew運用の実体験
  - あるクライアントのCTOと「AI時代の開発思想をどう組織に統一するか」を1時間議論（2026-08-03。守秘のため社名・数値は出さない）
  - 議論の準備として開発手法の全体整理資料と、組織移行計画のドラフトを作成済み（Obsidian: Work/Makuake/20260804_開発手法の整理.html / 20260804_AI時代の開発体制移行_draft.html — **記事化の際は必ず抽象化・匿名化**）
- 筆者の問題意識:
  - ウォーターフォール、アジャイル、DDD、BDD、TDD、DevOps…を「どれを選ぶか」の同じ土俵で並べる議論が多いが、**これらは軸が違う**。進め方（WF/アジャイル=択一）・設計思想（DDD/BDD/TDD=層の道具で併用可能）・運用文化（DevOps/SRE=独立に導入可能）
  - 各手法は前時代の痛みへの反動の連鎖として生まれた（WFの手遅れ→スパイラル→アジャイル→速く作っても運用が壁→DevOps→Vibe Codingの制御不能→スペック駆動）。**歴史の因果で読むと丸暗記が要らない**
  - AI時代の結論は3つ:
    1. **曖昧さの許容だけが消える**。人間は曖昧な指示を背景知識で補完できたが、AIはできない。反復（アジャイルの本体）は残り、サイクル内の要件・設計をかっちり書かざるを得なくなる=「本当の意味でのアジャイル」
    2. 手法は権限のレイヤーに配置する: 憲法（Why最上位）→目的→語彙（DDD）→仕様（BDD/仕様駆動）→テスト（TDD）→実装（AIに委任）。下位が上位に反したら上位が勝つ、のルール1本
    3. **「開発哲学の組織統一」は思想教育では実現しない**。「各層の守り手（手法）を組織として固定し、チケット書式と検証の仕組みに埋め込む」問題に変換する。思想は語って浸透させるものではなく、仕組みに埋めるもの
  - 話題のスペック駆動開発（Kiro/Spec Kit系）は新発明ではなく「仕様駆動+TDD+小さく回すアジャイルの再結晶」。requirements/design/tasksは要件定義・設計・作業分解であり、3点セットを収める器がチケット
- ラベル: ストック型（「開発手法 歴史」「DDD TDD BDD 違い」「AI 開発手法 組織」検索）+ 主張型（結論3つ）
- パターン: 解説 + 主張（歴史パートは地図、結論パートは体験に載せる）
- 前作との関係: [[20260413_ai-waterfall-agile]]（個人開発でのWF/アジャイル論）の**組織版続編**。前作「AIが来たらWaterfallが戻ってきた（と思ったらAgileだった）」の問いを組織スケールで再演できる
- 読者メリット: 手法名の洪水で迷子のエンジニア・EM・CTOに「軸の違い」という地図を渡す。AI導入で「思想をどう揃えるか」に悩む組織への実践解（仕組みに埋める）

- **記事の核（重要）**: 手法カタログ・歴史年表の記事は無数にある。核は (1) **「同じ土俵ではない」— 軸と層に分けて配置する地図** と (2) **「哲学の統一は仕組みへの埋め込みに変換する」という組織論の結論**。この2つを外すと「まとめ記事」に堕ちて刺される
- 反論材料（先回り）:
