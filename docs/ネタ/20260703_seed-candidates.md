## 候補 #1: 要件定義書は読まれない。AIにmockを作らせたら、すり合わせが一瞬で終わった

- **ステータス: 調査中（2026-07-03 筆者持ち込みテーマ。調査 → ドラフト作成の方針決定済み）**
- ソース: 筆者持ち込み + セッションログに周辺の裏付け
  - 「要件定義書通りに実装されていなかった」「要件定義書の説明に長時間かかる」等、ドキュメント駆動のすり合わせが機能していない事案が現場に複数（機密のためテーマレベルに抽象化）
  - 筆者は要件定義書生成スキル（ugroup-skills:requirements）を自作 — 「ドキュメント整備した本人が、それでも mock の方が伝わると言う」構図
- 筆者の問題意識（2026-07-03 修正版・原文趣旨）:
  - AI主体の開発において、AIにコーディングさせる側はハーネスエンジニアリングが流行った。しかし組織で開発する以上、**エンジニア以外の職種への説明責任**がある
  - 普段は要件定義書を書いているが、**要件定義書は自分（とAI）用に書き、説明用にはmockを作って認識をすり合わせる**方が早いのではないか
  - これが主流になった方が生産性が上がりそうだと感じている
  - 注意: dev-crewでmockを作っている、という話では**ない**（初版の記述は誤り）
- ラベル: フロー型（主張型・議論喚起）+ ストック型の面（「AI プロトタイピング 要件定義」「モックファースト」検索）
- パターン: 体験記（筆者指定。主張は体験に載せる）
- 読者メリット: 受託・社内開発で「要件定義書を読んでもらえない／認識がずれる」に悩む PM・エンジニアへの実践的な代替案
- ピックアップ狙い: 条件付き（不足: mock のスクリーンショット or 具体的なすり合わせ事例1本）
- 判断3条件: 実体験[○] 読者メリット[○] 差別化[○に近い]
- **記事の核（重要）**: 「mock 駆動」自体はプロトタイピングモデルとして昔からある。核は「mock が新しい」ではなく、**AI で mock 作成コストが崩壊したので、昔は割に合わなかった使い捨て mock 駆動が主流になり得る**という点。ここを外すと「昔からあるよ」と刺される。ここを軸にすれば差別化[○]
- 検討事項（執筆前に筆者確認）:
  - mock 事例のスクリーンショットを出せるか（守秘との兼ね合い。デフォルメ再現でも可か）
  - 「要件定義書が不要になる」ではなく「合意形成の主役が文書から mock に移る」トーンか（要件定義書スキルを自作している筆者の立場と整合させる）

### 調査結果（2026-07-03 note-research）

**類似記事と差別化ポイント**:
- [生成AIを用いてRFPからReactモックを2時間で作ってみた（Asia Quest）](https://techblog.asia-quest.jp/202509/ai-powered-rfp-to-mockup): Claude CodeでRFP→機能要件書→ユースケース→ワイヤーフレーム→Reactモックの4段階。提案スピード10日→2時間。**角度は営業提案の高速化**で、組織内の説明責任・非エンジニアとのすり合わせではない
- [非エンジニアでもできるConversational Prototyping（note）](https://note.com/happinessinsight/n/n3061fc74f831): 非エンジニアがAIでモックを作る話。**エンジニア側が説明のために作る本テーマとは逆向き**
- vibe coding 系記事多数（[豆蔵](https://developer.mamezou-tech.com/blogs/2025/08/19/vibe-coding/)等）: 要件定義とプロトタイプの並行はあるが、いずれも開発プロセス内の話
- **差別化の核**: 「要件定義書は自分とAI用（内部契約）、mockは非エンジニアへの説明用（対人インターフェース）」という**文書とmockの役割分担論**は見当たらない。ハーネスエンジニアリング（AIに書かせる技術）の次は説明責任、という接続も独自

**技術・市場の裏付け**:
- Lovableは公開60日でARR $10M、90日で$17M、8ヶ月で$100M（[Growth Unhinged](https://www.growthunhinged.com/p/lovable-growth-story)）— 「動くものを最速で作る」需要の市場実証。**注意: 初版メモの「2ヶ月で$20M」は誤りだった（integrityレビューで検出・記事は修正済み）**
- [Claude CodeのArtifacts機能（Zenn, 2026-06）](https://zenn.dev/canly/articles/64f112e3053834): 動くモックを組織内URLで配布、セッションが進むと同URLが更新される。「触れる体験デモが配れる恩恵が想定以上」
- 実例: bolt.new で30分試作→社内デモで方向性合意→翌週Lovableで本構築、という2段活用の報告あり

**反論材料（記事内で先回りすべき批判）**:
1. **プロトタイプの罠（古典）**: 動くプロトタイプを見たステークホルダーは「ほぼ完成」と誤解する。使い捨てである旨の期待値管理が必須（[TestMatick](https://testmatick.com/risks-of-prototyping/) 等）
2. **「プロトタイピングモデルは昔からある」**: 反論は「AIでmock作成コストが崩壊し、使い捨て前提が初めて経済合理的になった」
3. **mockに映らないもの**: 非機能要件・業務ルール・エッジケース・データ整合はmockでは合意できない → だから要件定義書は消えない（筆者の役割分担論と整合、むしろ補強材料）
4. **従来のプロトタイプ開発のデメリット**: 手戻り増・長期化 → AI時代は「作り直しコストが低いので手戻りが罰でなくなる」で返せる
